Self-managed GitLab · independent checker

Is your GitLab server exposed to CVE-2026-110264?

An integer overflow in Ruby's own regex engine (Onigmo). Any place where GitLab turns attacker text into a regular expression can reach it; the one route made public so far is GitLab's Org-mode (.org) renderer, reachable without login. Your version decides whether you are affected; the scans look for planted payloads. This page is static: your token and results go only between your browser and your GitLab.

CVSS 10.0 · unauthenticated RCE Fixed 21 Oct 2026 Affects 7.0 → 19.5.0 No official workaround
01

Identify your server

Without a token the page sees exactly what an attacker without an account sees: whether public projects are visible, and any payload planted in them. GitLab hides its version from anonymous visitors, so type it above if you know it. Add a token to read the version automatically and to scan internal and private projects too.

Requests go from your browser straight to your server. A token, if you give one, is never saved. 

      
Your server must use https (this page is https). If it is only reachable on your office network or VPN, connect first; your browser may ask to allow access to local network devices. Use an admin token to scan every project; a normal user token only sees projects that user can see. Create a short-lived token and revoke it afterwards.

04
Look for planted payloads

    
The bug fires when a regular expression with a huge number of repeats (over 32,767) is compiled. The scans flag two things:

    
    
      
  • Known payload a #+TODO:, #+SEQ_TODO: or #+TYP_TODO: line over 500 characters in an Org file. This is the route GitLab's detection rule describes. Upper or lower case and indented lines both count.
    • 
      
  • Review the same signature anywhere else in Org files and in GitLab CI config files (.gitlab-ci.yml, *.gitlab-ci.yml, .gitlab/**/*.yml): one short piece of text repeated 500+ times, or a line over 32,767 characters. CI config is where the same researcher reached the same regex engine in the 12 October CVE.
    • 
    

    
A clean scan does not make an unpatched server safe. GitLab has not published every route to the bug, and nothing outside your server can test routes nobody has described. Only upgrading closes it.

05
Check logs for attempts

    
GitLab published two Sigma rules for this flaw in its open-source TLDR repository: Org mode render error burst (5+ Org-mode render timeouts from one client within 30 minutes, in exceptions_json.log) and Onigmo native worker crash (in puma_stderr.log). Load them into your log tool. For a quick manual look:

    

    
A successful exploit can be quiet and does not always crash a worker, so a clean log is not proof. A crash is a reason to investigate, not proof of compromise.
